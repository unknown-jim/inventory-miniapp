# 记账约束和现场规矩

开发者不可能为各行各业的用法都考虑周全。不要把某一个现场的习惯写成软件限制。

差点出过的问题：把「退货成衣只能改黑、不能改尺码」写进扣账逻辑。那是某一家店的工艺，不是进销存必须成立的事。另一家店、另一种料，软件就会挡人。

## 两层不要混

**记账要自洽。** 件数不能凭空变多变少；退货回到当时卖掉的那一格；一张单里的待加工不能两行各算一遍。这不是行业规矩，是账对得上。详见 [blank-process.md](blank-process.md)。

**现场规矩交给用户。** 能不能换某一根轴、先改再卖还是当场改，由人决定。软件提供操作，不替用户裁判。

## 该做什么

- 提供显式操作：进货、销售、退货、改规格、期初欠款、库存调整。要加工就走「改规格」，不要藏在退货或销售里替用户猜。
- 库存调整只改用户点中的那一格件数，不更新进价，不计入进货金额、销售额、销售毛利和客户欠款，也不开送货单。花钱进货走进货；卖货走销售；退货仍绑原销售单；送货单赠品走销售、售价填 0；盘盈、盘亏、报损、无单赠品走库存调整。
- 上线前已经欠的钱走「期初欠款」。只加应收，不改库存、不计入销售和毛利。不要用假销售去凑欠款。
- 销售填**实收**，不选「现结 / 赊账」。开单时算出本单应收，实收默认等于应收，欠款 = 应收 − 实收。收一半也记得下。实收少于应收必须选客户：散客不能欠钱。多收的钱走「收款」，销售单里的实收不能超过应收，否则欠款会变成负数。
- 退货先冲这张单没收到的钱，冲不掉的部分才算退现金。卖 100 收 40 再退 30，是欠款从 60 变 30，不退现金。选这条而不是按收付比例分摊，是因为它的出错方向可补救：现场真退了现金，事后补记一笔收款就对上；按比例算错了要一笔负数收款，系统里没这个操作。全额退货两种算法结果相同，只有部分收款又部分退货才分得出来。实现见 [`utils/inventory.js`](../utils/inventory.js) 的 `returnCashRefund`：这一刀切在**写路径**，冲不掉的现金退款额记在退货单头的 `paidAmount` 上，不在读的时候现算（理由见 [docs/cloud-ledger.md](cloud-ledger.md) 的「结算口径」）。改销售单或改/删任何一张退货单时，系统把这张销售单的全部退货单按记账顺序整体重算现金退款额，店主不用先删后面的退货单。有退货的单也可以改单价：退货行的单价不是店主录的（退货页只收数量），是退货时从销售行复制过去的派生值，所以销售行改了价、同单退货行跟着按新价一起重算，口径等于手工的「先删退货 → 改价 → 重录退货」。不这样做，同一张单里同一件商品就有两套价，销售额、毛利、欠款三个数都是拼出来的。账面退款额会跟着变，当初实际退出去的现金不会变 —— 抽屉里到底是多少只有店主知道，所以销售详情页保存前提示一次，核对交给人。
- **欠款夹断的单位是整张销售单，不是行**：`欠款 = max(0, 单据应收 − 单据实收 − 单据已退货值)`。实收和欠款都记在单头，退货冲的是「这张单还没收到的钱」，不问退的是哪一行。例：整单应收 200、实收 100（钱照着第 1 行收的）、只退第 1 行 50，欠款是 `max(0, 200 − 100 − 50) = 50`，不是 100。按单夹断是流水改成「一单一记录」（`c1e40b5`）之后的必然结果 —— 此前一行商品一条流水，夹断只能按行；也更贴合现场：实收没有行级归属（店主收的是一笔钱，不是「第 2 行的钱」），按行夹断得先把实收摊到行上，摊法只能靠猜，而店主看到、改、退的本来就是一张单。**老账的欠款会跟着变**：夹断不可加（`Σmax(0, ·) ≥ max(0, Σ·)`），换单位之后同一批老流水算出来的欠款**只会不变或变小，不会变大**。差异出现在「钱没收齐、货又没全退」的单上（整单没收钱、全额收款、全额退货这三种，两种算法结果相同），这类单并不罕见——审计跑的 240 组老数据语料里有 86 组逐分不同。迁移后先照着有欠款的客户对一遍账：差额是口径变了，不是记错了。
- 操作便利：新建商品时**先选类型**，也可先点**种类模板**带出可改、可删、可追加的名称和规格待选项。待选项是起点，不是名单。
- 多规格可以勾「同价」，只填一次进价售价。这是建档便利；进货仍可改某一格的进价。
- 规格叫什么、取值是什么、改成哪一格，都由用户填写或点选，不要写死「只能改成黑色」或「轴必须叫颜色和尺码」这类行业假设。

## 看板今日五数（实收 / 未收怎么算）

看板首屏的今日数字是五个：**实收 / 应收 / 未收 / 毛利 / 进货**。hero 大数字是实收，副行是「今日应收 ¥4,120.00 · 其中未收 ¥260.00」，两格 stat 是毛利和进货。取数在 [`utils/inventory.js`](../utils/inventory.js) 的 `todayTotals`，服务端按客户端给的 `dayStart` 现算，客户端一行都不算；`getDashboard` 把它投影成 `todayReceivedAmount` / `todayUnreceivedAmount`，算不出来时和其余今日数一样给 `null`（页面显示「—」，不是 0）。

口径：

- **今日应收** = 今日销售单应收合计 − 今日退货单货值合计。就是原来的 `salesAmount`（四宫格时代叫「今日销售」）。**不另开字段**：同一个数两个标签，开两份就多一处要对账的地方。
- **今日实收** = Σ今日销售单实收 − Σ今日退货单退现金。
- **今日未收** = 今日应收 − 今日实收。

三个数因此满足 **实收 + 未收 ≡ 应收**，逐分成立（整数分累加；未收由「应收 − 实收」构造出来，不是另折一遍再指望它相等）。这条恒等式是硬约束，不是巧合：看板把三个数并排画成一句话，店主一定会做那个加法。

**收款（`pay`）和期初欠款（`opening`）不进这三个数。** 「今天收了昨天的欠款」不抬今日实收 —— 收款没有应收可以配，掺进来恒等式当场变假，屏上三个数就加不起来了。这笔钱不是丢了：它落在看板的欠款横幅（`totals.receivable`）上，收一笔横幅降一笔。要「今天进账多少」那种现金流口径的数，那是另一个数、另一个标签，不要塞进「实收」——「实收」在这个仓库里从来就是销售单上那个字段。

**退货按它自己那一刀进**（先冲这张单没收到的钱，冲不掉的才算退现金，见上面那条）：冲欠的部分压低未收，退现金的部分压低实收，货值整体压低应收。所以「卖 100 收 40 再退 80」那个例子在看板上是今日应收 20 / 实收 20 / 未收 0。

**未收可以是负的。** 昨天赊的货今天退掉，今日未收和今日应收一起变负 —— `salesAmount` 本来就会在这种日子变负，不是新冒出来的怪相，照实显示即可。**不要夹成 0**：夹一下恒等式就断了。

**与预收（G1）的口径对齐**：预收永远不进今日实收。`settledAmount` 把销售单实收夹在单据应收之内，超收的那部分不是「本单实收」；将来放开欠款那个 `max(0, ·)` 夹断去做客户余额时，**不要顺手把 `settledAmount` 的上夹也放开**，否则今日未收会变成负数、恒等式跟着断。独立记的预收与 `pay` 同类，同样不进。

**演示账（设计稿 `9:18` 对照表）复算。** 表里逐笔声明的只有王姐 014（应收 352 / 实收 268 / 欠 84）和李老板枕芯（128 现结），其余是背景账；按上面的口径，背景账那一块自己也闭合 —— 应收 3640 = 实收 3464 + 未收 176，合起来正好 **4120 = 3860 + 260**。用例钉在 [`tests/inventory.test.js`](../tests/inventory.test.js) 的 G3 一节。表上 15:10 那张退货单（96 = 冲欠 84 + 退现金 12）按本口径是要进这五个数的（算出来应收 4024 / 实收 3848 / 未收 176）；演示账把它挡在外面，是「看板今日五数是背景账、不参与逐笔勾稽」那条裁定放行的**演示账特例**，不是公式的反例。

## 不要做什么

- 不要按「服装厂通常……」去限制库存怎么转，也不要把类型和规格轴写成只服务衣服。
- 不要在退货里夹带换格、当待加工用。退货只负责原样入库。
- 不要为了表达「收了一半」去拆成两张销售单，也不要先记全额赊账再补一笔收款凑数。实收就是给这件事用的，凑出来的流水对不上当时到底收了多少。
- 不要为了省一次点击，让销售偷偷拿其他规格去充当前规格。
- 不要把待选项做成唯一合法值。
- 不要在代码里预置「纺织」「零食」这类行业种类。种类模板由用户增删；示例数据可以带两份给人改。
- 不要把「待加工」做成跨商品原料仓或配方。待加工是**这件商品自己的未分格库存**。

需要新人把关、严禁某种改法，是店里的管理问题，不该用隐藏规则补。
