# 提交说明与 Pull Request

本文件是仓库级约定，给人和各类 Agent 共同遵守。不要把同一套规则只写在 `.cursor/` 里。

分支怎么开、工作树怎么放，见 [git-workflow.md](git-workflow.md)。本文只规定：**一条 commit 和一份 PR 怎么写、一次改动多大**。

## 依据

- [Writing good CL descriptions](https://google.github.io/eng-practices/review/developer/cl-descriptions.html)（Google 工程实践：变更说明）
- [Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)（Google 工程实践：小变更）

这是 Google 公开的工程实践，不是 Conventional Commits，也不是本仓库自创的「最佳实践」。下面的「必须 / 建议」以这两份材料为准；「本仓库怎么做」按当前形态推导：GitHub、中文沟通、单人本地微信小程序、历史用 Merge pull request 合入。

**前提：** 读者会用 `git log` 和 GitHub PR 找回一次改动；合入后的说明要在几年后仍能单独看懂。

**不适用：** 把一个 10 行热修拆成多份 PR；或只写 `feat:` / `fix:` 标签、正文留空。标签代替不了「改了什么、为什么改」。

## 本仓库怎么映射

Google 内部的 CL（changelist）对应「一次可独立理解和合入的改动」。在本仓库：

| Google | 本仓库 |
|---|---|
| CL 首行 | commit 首行；squash 合入时也是 PR 标题 |
| CL 正文 | commit 正文；PR 正文是给审阅者的封面，须包含同样的「做什么 / 为什么」 |
| 一系列小 CL | 一系列小 PR，或一份 PR 里若干条已经写清楚的 commit |

提交说明会进版本历史，可能被以后的人按关键词搜到。代码能回答「现在做什么」，说明要回答「当时为什么改成这样」。

## 1. 提交说明

### 首行

- 用**祈使句**，像在下指令：写「删除过期的占位数据」，不要写「删除了过期的占位数据」或「正在删除…」。
- **单独成立**：只看这一行，不必打开 diff 也能和别的提交区分开。
- 先写**具体做了什么**，不要先写过程或口号。
- 尽量短。中文建议不超过约 40 字；GitHub 和 `git log --oneline` 都会截断长首行。
- 首行**不要**以句号 / 句点结尾。
- 正文之前空一行。

可选的短范围前缀（Google 允许 tag；Go / Chromium 常用 `area:`）。前缀要短，不要堆多个长标签：

```text
流水: 允许从已有记录再次导出送货单
docs: 规定提交说明与 PR 的写法
tests: 为收款弹层补上自动点击用例
```

范围用**被改的模块或页面**（`商品`、`销售`、`流水`、`docs`、`tests`），不要用 Conventional Commits 的类型词（`feat`、`fix`、`chore`）当主语。分支名仍用 [git-workflow.md](git-workflow.md) 里的 `feat/` `fix/` `docs/` `chore/`，那是分支分类，不是 commit 首行格式。

### 正文

首行是摘要；正文补全审阅者和未来读者需要的上下文：

1. **问题是什么**（不改会怎样）
2. **为什么这样改**（包括不写进代码里的取舍）
3. **方案的不足**（如果有）
4. **背景**：相关 Issue、设计讨论、对比数据（如果有）

外链可能失效或需要登录。能写进正文的关键信息，不要只藏在链接里。

很小的提交也要有一点上下文，不要只重复 diff 里已经能看见的「把 A 挪到 B」。

commit 正文用纯文本，不要用 Markdown 标题。需要换行时按终端可读来折，避免一整段超长行（URL、表格除外）。

### 不要这样写

这些首行信息量不够，以后没法搜、没法区分：

- `修 bug`
- `fix build`
- `更新代码`
- `feat: 添加功能`
- `Phase 1`
- `改一下`
- `WIP`

### 可以这样写

功能：

```text
流水: 允许从已有记录再次导出送货单

销售当时若没勾选导出，事后只能再走一遍销售。
从流水再导出只复用当时的客户、商品和数量，不改库存。

在微信开发者工具里：销售一笔且不导出 → 打开流水 → 再导出，
核对送货单与当时销售一致。
```

文档：

```text
docs: 把 Git 工作流基线从 master 改为 main

GitHub 默认分支已是 main。继续从 master 开任务会把历史分支当基线。
本变更只改约定文档，不改产品行为。
```

修复：

```text
销售: 库存不足时禁止提交出库

原先只在输入时提示，提交仍可能写成负库存。
提交前再读一次本地库存；不足则拦截并提示，不写流水。

npm test 覆盖「库存 1 卖 2」；开发者工具里手动提交一次确认弹窗文案。
```

工具生成的说明（Agent、IDE 默认模板）也要改到符合上面几条。默认的 `Update foo.md`、`Generated by ...` 不能直接当历史记录。

### 合入前再看一遍

审阅过程中 diff 常会变。合入前核对首行和正文是否还等于**现在**这份改动。过时的说明比没有说明更误导。

## 2. Pull Request

PR 是给人审的 CL。标题和正文要让没有一起写代码的人，不读完所有文件也能判断：该不该合、从哪看起、怎么验。

### 标题

与 commit 首行同一套规则：祈使句、单独成立、短、无句末句号。若 GitHub 使用 squash，标题会成为 git 历史里的那一行，更不能写 `WIP` 或 `fix stuff`。

### 正文

建议按这个顺序写（小节标题可省略，内容不要省）：

```text
这次改动做了什么，解决什么问题，为什么现在改。

若有取舍：为什么不选更小/更大的方案，已知不足是什么。

测试：
- [ ] npm test
- [ ] （若动了点选、收款、送货单）npm run test:ui
- [ ] 微信开发者工具里按「怎么验」走一遍

怎么验：用开发者工具能复现的步骤，写清数据前提和期望结果。
```

不要把正文写成文件清单。diff 已经有文件清单。正文要写 diff **看不出来**的动机和风险。

相关 Issue 用 `Fixes #123` 这类 GitHub 关键词放在正文末尾；不要让它取代「为什么改」。

### 一次 PR 多大

对标 Google 的「一个自包含变更」：

- 只做一件事。通常是功能的一部分，而不是整条产品路线一次合完。
- 相关测试和这次逻辑放在同一份 PR 里。
- 审阅者只靠这份 diff、这份说明、已有代码、已经合入的 PR，就能理解；不要默认对方记得聊天记录。
- 合入后程序对使用者和开发者都仍然可用（不要「上半截先合、小程序暂时打不开」）。
- 也不要小到看不出意图：新 API / 新工具函数至少带一处真实用法。

没有行数硬门槛。Google 原文的经验是：约 100 行往往好审，约 1000 行往往太大；摊到很多文件上会显得更大。本仓库页面少，更常见的过大是「一次 PR 塞进互不相关的功能、重构和文档」。有疑问时偏小，不要偏大。

可以较大的情况：整文件删除、完全可信的自动重构（审阅者只确认「确实要这么改」）。

### 怎么拆

- **重构和功能分开。** 重命名/搬家不要和修 bug 混在一次 PR。改局部变量名这种小清理可以夹在功能 PR 里。
- **先可合的底层，再依赖它的界面。** 例如先合数据层校验，再合销售页按钮；每一段合入后小程序仍能用。
- **不要为了「显得小」把一次热修拆碎。** 拆完后每一段都应该能单独理解、单独回滚。

### 审阅期间

- 评论里补充的设计取舍，若以后读历史还需要，请写回 PR 正文或代码注释，不要只留在会被折叠的讨论里。
- 合入前再读标题和正文，使之匹配最终 diff。

## 3. Agent 检查清单

写 commit 或开 PR 之前：

- [ ] 首行是祈使句，单独能看懂，没有句末句号
- [ ] 没有用 `feat:` / `fix:` / `chore:` 代替具体说明
- [ ] 正文写了为什么改，而不只是复述 diff
- [ ] 有对应的测试或「怎么验」步骤（纯文档可写「只改文档，不改产品行为」）
- [ ] 一次 PR 只做一件自包含的事；重构没有和功能混在一起
- [ ] 合入前说明仍与最终 diff 一致
